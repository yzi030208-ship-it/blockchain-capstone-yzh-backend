## 老师要求与实现边界

依据《大作业要求》PDF 第 16 页，本项标为 3 分：新增 Shipped 状态和 markShipped(id)，买家超期退款仅在未发货时允许，并更新测试、页面或接口。每项加分材料在报告中单独提供截图与说明；分数及总加分上限以课程任务书为准。

本项目走路线 A，采用合约、生成封装、后端查询接口及测试一起更新的方案，不要求为了本项另做路线 B 前端。发货交易必须由实际卖家账户签名；后端已有仲裁账户不能凭客户端传来的 seller 地址冒充卖家。可由卖家在 Remix 附加新合约发送 markShipped，后端接口提供状态和事件查询。

原合约不是可升级代理，也没有 markShipped，原两单已结束。应为本项部署新的发货扩展版 Escrow，使用原组代币和新实验订单。原主业务 Escrow `0xDb666Df58291D7d49cea35eE36929dCcD37e2ea5`、原交易和时间线证据保留，不对其重复发送操作。新地址和订单要明确登记到报告 4.5 的本项，不能混写成原主业务部署。

### 一 先完成代码和本地验证

从项目最新代码建立单独发货功能分支，不继续向订单时间线 PR #4 塞入发货代码。原有未提交的独立重入挑战材料保持独立。

需要修改并验证：

- 增加 Shipped 状态。若保留既有状态编号，追加为 5，原 Created/Paid/Completed/Refunded/Disputed 的 0 至 4 不变；Java 状态名称映射同步。
- markShipped(id) 仅允许订单卖家对 Paid 订单调用，状态改为 Shipped，发出 OrderShipped(id)。
- 买家 refund 仍要求本人、Paid 且超过 deadline；Shipped 不得退款，不能只检查时间。
- 本项扩展版的正常确认流程设计为 Paid → Shipped → Completed；相应更新 confirm 的状态条件和测试。争议处理需覆盖已付款或已发货订单，避免发货后失去申诉入口。以上为实现方案，不把老师未明确的细节写成原文要求。
- 新生成 ABI/Java 封装，确保部署字节码、状态映射、事件签名与实际源码对应；接口能显示 Shipped，时间线能解码 OrderShipped。
